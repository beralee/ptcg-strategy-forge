# PTCG Base 策略构筑与复盘

把牌组理解变成可执行的局面判断、资源约束和逐步重规划。交付精确 `.ptcgai`、可复现证据与已知缺口；每轮经验只在有证据时沉淀为通用框架能力。

## 开始或续作

- 确认实际 Forge 根目录、`AGENTS.md`、工作树和已有研究状态，按仓库要求阅读。维护源是 Forge 的 `skills/ptcg-strategy-base/`，安装副本在 Codex skills 目录；修改后同步并校验摘要。
- 新牌组固定精确 60 卡、印刷 UID、SDK 和基线；已有策略先读最后回执，核对实际文件摘要。不要由牌组名称或历史成绩推定当前包相同。
- 本 skill 适用于规则底座。任务涉及 BC、神经网络或 PPO 时，以可用的 `ptcg-learned-strategy-pipeline` 为主要训练流程，本框架只承担可审计规则底座。不要自动启动训练。
- 用户只要求框架、skill 或审查时完成该范围；要求构筑/优化时持续完成相应开发与验收。已有上传授权按具体策略和会话范围判断，不由本 skill 推导其他包的上传、安装、Git 提交或外部仓库权限。

## 构筑与多步决策

读 [框架使用](references/framework.md)。使用现有 `StrategyWorkspace` 创建牌组工作区，再运行 `tools/strategy_base.py init`。该工具要求 Competitive IR v2；v1 必须先审查并迁移，不能只改版本数字。

1. 在 `base/plan.json` 审核全部 16 项考虑事项。为每项填写具体牌组理由，标为 `implemented`、`gap` 或有理由的 `not_applicable`；不能批量把未知标为“不适用”。`implemented` 要引用实际规则/目标/路线 ID，但引用存在不证明行为正确，仍需场景和实战。
2. 从胜利条件和最紧缺资源出发，编写少量关键路线。每条路线按**当前局面能够重新证明的阶段**拆开；每阶段写 guard、精确目标、剩余费用、信息检查点和类型化交互。预算从本窗口起算，不再次索取前缀已花掉的手贴/支援者。
3. 比较攻击窗口、奖赏推进、后继连续性、成本、反制风险与不确定性。整数值是人工排序，不能称为获胜概率。费用必须落到同一实体；特殊能量、一次性能力和退场代价要检查具体印刷。对手未知手牌、未来抽牌和奖赏身份都不是证明。
4. Base 保留当前合法集合、mandatory/terminal、hard tier、veto、数量和 fallback。每步接受后重新观察；后续阶段必须重新满足 guard 和当前选项，不保存旧索引、分数或证明。未知事实应关闭依赖它的路线。
5. 先用 `audit` 找遗漏，再 `compile` 生成候选 adapter；保存原包，在候选工作区应用并按仓库要求完成 RED→GREEN、重排、负例、信息分支和 `check`。不要为了挤过 32 条路线限制静默截断候选。

蓝图起点见 [策略蓝图](assets/STRATEGY-BLUEPRINT.md)。基于多龙的经验，特别检查：当前攻击前的解围、同一只攻击手的精确费用、后继和过牌引擎、死手可用性、备战位及奖赏负担、零前场伤害时的后排/封锁价值、自爆送奖与牌库耗尽。它们是需要评估的问题，不是对所有牌组一律打高分的规则。

## 录像驱动的自动迭代

读 [复盘与持续迭代](references/iteration.md)，以 [迭代记录](assets/ITERATION-RECORD.md) 记录当前轮。

在一次已授权构筑/优化任务中，主动完成“校验录像 → 提炼假设 → 首个分歧 → RED 场景 → 最小修复 → 安全回归 → 完整链 → 工作区验收 → 配对评估 → 接受或回滚”。常规步骤无需逐次确认。保存状态后续作从最早未过的门开始，不重跑无关阶段。

- 自动检测只生成优化假设。必须结合精确卡效和完整上下文审查；没有执行的替代分支不能计为翻盘或训练标签。
- 先定位 observation、identity、interaction、adapter、Base 或 engine 的最早责任层。策略层错误修策略；确属通用能力缺口时先加跨牌组反例，再修框架及其测试，不能把某牌组权重写成通用默认。
- 迭代由 agent 按 skill 执行，不是后台自修改服务。遵守用户预算；未给预算时先选择一个最高价值假设完成聚焦修复和小额开发评估，再依据证据与成本决定后续。用户停止、资源保护触发、外部必要接口缺失或既定预算结束时保存失败/待办状态，不自动重试资源故障。
- 新机制至少覆盖原牌组和另一种角色/费用结构的独立例子。只有合成例子时明确标为公开窗口能力，不能声称新牌组实战强度。

启动重型评估前检查本机 Python/Godot、RAM、commit 和实际磁盘；遵守仓库保护与监督器，重型任务串行、最多 4 workers。轻量场景和合同测试先于整局。不要为完成框架/skill 创建任务自动启动新 benchmark。

## 交付

交付候选与回滚身份、代码/SDK/牌表/套件/录像摘要，以及实际关闭的门。分别报告编译、公开窗口模拟、引擎见证、强度、平台资格与未支持范围。同步有证据的经验到 skill 和框架文档；只保留能改变后续决策的规则，不堆积每个失败局的特殊禁令。
